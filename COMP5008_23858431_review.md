## F04 - Medium: nearly-sorted inputs do not consistently displace 10% of records

**Requirement:** Section 7.2.4 specifies nearly sorted input with 10% of records displaced.

**Where:** `module4_sorting/collection_records.py:79-93,107-114`; `module4_sorting/benchmark_sorting.py:197-203`.

Pairs are chosen with replacement. A position can be chosen twice, a swap can select the same position twice, and later swaps can undo earlier ones. Therefore `n/20` swaps guarantee at most 10% displacement, not the required 10%.

The archived output itself shows the shortfall, independently reproduced with record identity:

| Size | Required displaced identities | Actual |
|---:|---:|---:|
| 100 | 10 | 10 |
| 500 | 50 | 46 |
| 1,000 | 100 | 98 |

Also, `countDisplaced()` compares transportation-time values, not record identities. Equal-T records can change position while this counter reports no displacement. The counts happen to agree in these saved runs, but the measurement is not generally correct for records.

**What to do:** manually select distinct positions and use disjoint pairs, preserving the fixed seed. Measure movement by record identity/ID, not only T. Regenerate timings, chart and any report numbers affected by the changed inputs.

**Verification:** require exactly 10, 50 and 100 identities to move relative to the sorted baseline; confirm no record is lost/duplicated and both algorithms receive identical input copies.

## F05 - Medium: EOF causes an infinite numeric-input retry loop

**Requirement:** Section 9.5, relevant input/error handling.

**Where:** `interactive_menu.py:39-62,260`.

`ask()` converts EOF into the string `"0"`. This is useful for menus where 0 means Back, but `askInt()` requires 10-1000 records. It rejects that 0 and asks again. EOF never changes, so it loops and prints indefinitely.

**Reproduced:** invoking the numeric prompt with closed stdin did not exit and required timeout termination. The same condition occurs when redirected input ends after choosing a sorting algorithm.

**What to do:** distinguish EOF/cancellation from the integer zero, and propagate that condition out of the numeric prompt/menu. Do not retry forever when no further input can arrive. Consider clean KeyboardInterrupt handling as well.

**Verification:** test immediate EOF, EOF at each nested prompt, invalid text followed by a valid number, and cancellation/back behaviour. Normal invalid input should still allow a retry.

## F07 - Medium: the hash API permits invalid entries and a duplicate-None failure

**Requirements:** Sections 5.2.3 and 5.2.5: duplicate handling, valid IDs and missing/invalid records.

**Where:** `module2_hash/hash_table.py:35-47,70-76,90-109`; validation currently occurs in selected callers such as `farm_record.createRecord()`.

**Reproduced through the public table API:**

- Inserting key `"bad id"` with value `None` returns True.
- Inserting the same key/None again also returns True; count becomes 2.
- `search(None)` raises an unhandled `TypeError` at the key-length/hash operation.

**Why:** `insert()` uses `search(key) is None` to mean “key absent”, but a present entry with a stored None value produces the same result. It also does not enforce a key/value contract itself.

The ordinary menu's farm-input path rejects many invalid records, so this is not a claim that those normal validations never work. The defect is exposed at the table boundary, and the current demonstrations do not test it.

**What to do:** define/enforce valid keys and payload rules. Either reject None payloads or detect key existence independently of its stored value. Farm-record validation must remain in the farm insertion path. Remember that this implementation also uses tables for pending request strings; do not unnecessarily restrict every table instance to FarmRecord values.

**Verification:** test invalid key types, blank/malformed IDs, invalid/missing payloads, duplicate keys, and duplicate handling after a tombstone. Rejected operations must not alter the count or existing records.

## F10 - Medium robustness limitation: equal keys cause deep Quick Sort recursion

**What to do:** accurately discuss the implementation's duplicate-heavy worst case and its recursion constraint. Quadratic worst-case time is an inherent allowed Quick Sort trade-off, not proof the required ordinary benchmark is incorrect. The specific concern is the demonstrated runtime failure and the hidden interpreter-wide workaround.

**Verification:** test all-equal, duplicate-heavy, ascending, descending and ordinary random arrays when importing the sorting module alone. Confirm record preservation as well as sorted order.
